Дневник на SQLite + SQLCipher: работает и на Windows, и на Linux

На Windows приложение не запускалось из-за отсутствия готового колеса sqlcipher3-binary. Причина найдена, зависимость заменена на кросс-платформенную, установка и работа проверены на обеих системах. Формат базы не менялся — данные переносятся без миграции.

Проблема

Воспроизведено в чистом виртуальном окружении на Windows x64, Python 3.12.8:

> python -m pip install sqlcipher3-binary
ERROR: Could not find a version that satisfies the requirement sqlcipher3-binary (from versions: none)
ERROR: No matching distribution found for sqlcipher3-binary
EXITCODE=1

Дальше в приложении не срабатывали ни import sqlcipher3, ни запасной pysqlcipher3; скрипт печатал «не установлен SQLCipher» и завершался с кодом 1. На Linux тот же код работал — значит, дело было только в зависимостях, а не в логике дневника.

Причина

Опрошен актуальный индекс PyPI. Пакет sqlcipher3-binary публикует исключительно сборки manylinux для x86_64 и не предлагает установку из исходников — под Windows у него нет ничего.

Решение

Драйвер заменён на sqlcipher3 0.6.2: тот же импортируемый модуль, тот же DB-API, тот же формат базы SQLCipher 4 — но опубликованы готовые колёса и для Windows, и для Linux, поэтому компилятор и OpenSSL SDK не нужны. Дополнительно в requirements.txt добавлен windows-curses под маркером sys_platform == "win32" — без него на Windows не работал полноэкранный интерфейс.

Что сделано в коде

  • порядок импорта sqlcipher3 → pysqlcipher3 с понятным сообщением об установке;
  • фолбэк совместимости: база, созданная SQLCipher 3.x, автоматически переоткрывается через PRAGMA cipher_compatibility;
  • глушение отладочного вывода SQLCipher, который ранее попадал в stdout;
  • путь к базе переопределяется переменной DIARY_DB;
  • неинтерактивные команды для скриптов и CI, вывод в JSON;
  • редактор notepad по умолчанию и включение ANSI-цветов в консоли Windows.

Существующая база .diary.db (20 480 байт, кратно 4096) осталась нетронутой: её резервная копия побайтово идентична исходнику, обычный SQLite её не читает, а SQLCipher с произвольным паролем отказывается открывать — то есть это действительно зашифрованная база. Пароль в коде не хранится, поэтому содержимое именно этого файла проверяется вами командой doctor.

Компромиссы и ограничения

  • Версия драйвера зафиксирована (sqlcipher3==0.6.2) ради воспроизводимости сборки.
  • Google API тянет около 16 МБ. Это сохранение прежнего поведения; без синхронизации эти строки можно удалить.
  • Резервная копия делается через VACUUM INTO — файл согласованный и зашифрованный, но не побайтово равный исходнику. Фолбэк на копирование файла встроен.
  • CI на GitHub не запускался — репозитория на GitHub у проекта нет; файл workflow готов и заработает после git remote add и push.
  • Проверка TUI на Windows выполнена в ConPTY, а не в устаревшем conhost.exe.
  • Linux проверялся в WSL2 (Debian); использованные колёса — manylinux, то есть переносимые.

Откат

  1. Восстановить исходный скрипт: Copy-Item .\TUI.py.orig .\TUI.py -Force (Windows) или cp TUI.py.orig TUI.py (Linux).
  2. Вернуть в requirements.txt пакет sqlcipher3-binary — это снова сломает Windows, поэтому только как крайняя мера.
  3. Файл базы откатывать не нужно: формат не менялся, база читается и старой, и новой версией.
  4. При необходимости восстановить базу из резервной копии, сделанной командой backup.
Отчёт построен только на зафиксированных результатах прогонов: вывод установщика, коды возврата команд, результаты pytest и selfcheck.py, сверка манифестов базы между ОС и наблюдения интерфейса в псевдо-терминале. Непроверенным остаётся содержимое личной базы .diary.db, пароль от которой недоступен инструментам проверки.
